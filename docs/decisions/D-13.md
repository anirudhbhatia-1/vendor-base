# D-13 — Resume Supabase as the synthetic development database

**Status:** APPROVED — DATABASE-ONLY REMOTE DEVELOPMENT ACTIVE  
**Accountable owner:** Project Owner with Engineering Lead  
**Decision date:** 29 August 2026  
**Production authority:** None

## Context

D-12 paused the earlier online-test environment and required a new explicit decision before any
online resource was used again. The project owner has now explicitly asked to use Supabase as the
database for current development.

## Approved decision

Add a `supabase-dev` target in which:

- the NestJS API and worker continue running on the developer computer;
- Supabase hosts PostgreSQL/PostGIS only;
- all records remain synthetic company-development data;
- OTP, payment, payout, maps, notifications and object storage remain local fake/filesystem
  adapters;
- reviewed repository migrations remain the only schema authority;
- no client connects directly to Supabase and no Supabase service key enters a client bundle;
- the local and isolated-test database targets remain supported as fallback and CI authorities.

## Safety boundary

- The database password previously exposed in development conversation must be rotated before use.
- The ignored `infrastructure/supabase-dev/.env` file is the only developer-file location for the
  connection string. Credentials are never committed, logged or pasted into documentation.
- Remote migration writes require an exact project-bound confirmation value.
- The target accepts only the selected Supabase direct or session-pooler host on port 5432.
- Development URLs without SSL parameters are normalized to encrypted, libpq-compatible
  `sslmode=require`. Production must install Supabase's CA and use `sslmode=verify-full`.
- The transaction pooler on port 6543 is not used for migrations.
- Destructive rebuild, reset, seed and rollback commands are not exposed for `supabase-dev`.
- This decision does not activate Cloudflare, OCI, R2, real providers, production data or public
  traffic.

## Consequences

- Developers can share one synthetic database while continuing to run application processes
  locally.
- Network availability and Supabase free-tier limits can interrupt development; local PostgreSQL
  remains the recovery path.
- Free-plan availability and backups are not production evidence. Production still follows the
  production-readiness plan and replacement register.
- Schema changes must be rehearsed against the isolated local test database before being confirmed
  against Supabase.
