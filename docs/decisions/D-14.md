# D-14 — Separate, least-privilege Supabase production database

**Status:** Accepted for implementation; production activation remains gated  
**Date:** 29 August 2026

## Decision

Production uses a Supabase project that is separate from development and staging. The NestJS API
and worker are the only marketplace data-access boundary; PWAs and Android applications never
connect directly to PostgreSQL or the Supabase Data API.

Two credentials are required:

- `postgres` is an operator-only migration identity, supplied only to an approved migration job;
- `marketplace_app` is a non-superuser runtime login and inherits permissions from the
  `marketplace_runtime` NOLOGIN role.

The `marketplace` schema and migration ledger revoke access from `PUBLIC`, `anon`, and
`authenticated`. Runtime receives only schema usage plus table DML, sequence use, and function
execution. Future objects inherit the same grants through default privileges.

Migration connections use direct or session mode on port 5432. API and worker runtime traffic uses
the least-privilege login through Supavisor transaction mode on port 6543; this codebase uses unnamed
queries and transaction-scoped locks, so it does not depend on unsupported session-level prepared
statements or locks. All connections require TLS hostname/CA verification through
`sslmode=verify-full` and the project-specific Supabase CA certificate. Migration execution remains
project-bound by an explicit confirmation value and an advisory lock.

## Operational requirements

- Supabase SSL Enforcement and Network Restrictions are enabled.
- Organization owners use MFA and at least two owners are available.
- Database changes come only from reviewed migrations; Dashboard schema edits are prohibited.
- A staging project rehearses every migration before production.
- A restorable backup exists before migration. Free-plan production is prohibited because backup
  downloads are unavailable and inactive projects may be paused.
- Recovery objectives, backup retention, restore drills, connection budgets, alert thresholds, and
  rollback ownership are documented before launch.
- Production runtime credentials live only in the deployment secret manager and are rotated.

## RLS boundary

The domain schema is not exposed to Supabase client roles, so authorization remains in the NestJS
service layer. If any marketplace schema/table is later exposed through the Data API, RLS and
reviewed policies become mandatory before that exposure is enabled.

## Consequences

The current `supabase-dev` project cannot be relabelled as production. Provisioning production
requires a separate project, paid backup/availability guarantees, dashboard security controls, and
new secrets. Repository controls can prepare and verify these requirements but cannot activate
account-level Supabase settings without an authorized Supabase Management API connection.
